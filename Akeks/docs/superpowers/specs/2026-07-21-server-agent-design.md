# Личный coding-агент на VPS, управляемый через Telegram

**Дата:** 2026-07-21
**Статус:** черновик, ожидает review

## Цель

Полноценный coding-агент (пишет код, коммитит, деплоит), который живёт на отдельной VPS и управляется с телефона через Telegram. Имеет доступ ко всем проектам пользователя на VPS и запрашивает подтверждение перед рискованными действиями.

## Область действия

- Движок: **Claude Agent SDK** (Python) — built-in инструменты (Read/Write/Edit/Bash/Glob/Grep) + полный agent loop, `canUseTool` hook для перехвата рискованных вызовов.
- Хостинг: новая, изолированная VPS (не используемый сейчас Beget-хостинг).
- Доступ: ко всем проектам пользователя (Akeks, content-agent-bot, lead-parser, Custom_Neuro_Marketolog1.0 и т.д.) с переключением командой.
- Интерфейс: Telegram-бот, единственный авторизованный пользователь.
- Подтверждение рискованных действий: inline-кнопки ✅/❌ в Telegram, блокирующие выполнение через `canUseTool`.

Вне области (не делаем в этой итерации): проактивные/scheduled задачи (агент чисто реактивный, отвечает на сообщения), веб-интерфейс, поддержка нескольких пользователей, observability-дашборд.

## Архитектура

```
Telegram (телефон)
   │  long polling (без webhook — не нужен домен/TLS/nginx)
   ▼
Bot Process (VPS, systemd service, Python)
   ├── python-telegram-bot — приём команд/сообщений, отправка inline-кнопок
   ├── Claude Agent SDK — по одной активной "сессии" на проект
   │      └── canUseTool hook → на рискованное действие шлёт inline-кнопки
   │          в Telegram, ждёт callback (asyncio.Future), потом разрешает/блокирует
   └── state (SQLite) — { telegram_user_id → активный проект, project → session_id }
```

Ключевые решения:

1. **Long polling, не webhook.** Бот сам стучится в Telegram API, входящих HTTP-запросов на VPS нет → не нужен домен/TLS/nginx, проще и безопаснее для новой VPS.
2. **Сессия на проект, не на разговор.** Agent SDK хранит `session_id` отдельно для каждого проекта. Команда `/project <name>` переключает "активный" проект пользователя, не теряя контекст остальных.
3. **Авторизация** — бот отвечает только на сообщения от `ALLOWED_USER_ID` (Telegram user id владельца, задан в `.env`). Сообщения от других id тихо игнорируются, но логируются.

## Компоненты

### Telegram Bot Layer (`python-telegram-bot`)
Хендлеры: `/start`, `/project <name>`, `/projects` (список доступных проектов из конфига), `/status` (текущий активный проект + состояние последней сессии), обычный текст (→ промпт агенту для активного проекта), `callback_query` (нажатия ✅/❌ на подтверждениях).

### Agent Core (обёртка над Claude Agent SDK)
`AgentManager` держит по одному активному клиенту SDK на проект, создаёт лениво при первом обращении к проекту. Список проектов задаётся в конфиге как маппинг имя → абсолютный путь (`cwd`) на VPS. Agent SDK сам подхватывает `CLAUDE.md` проекта из `cwd`.

### Confirmation Bridge
Словарь `correlation_id → asyncio.Future`. `canUseTool` при рискованном вызове инструмента:
1. Классифицирует вызов (см. ниже) как risky/safe.
2. Если risky — создаёт future, отправляет в Telegram сообщение с описанием действия и inline-кнопками (`callback_data = correlation_id:yes` / `correlation_id:no`), ждёт future с таймаутом (по умолчанию 10 минут).
3. `callback_query`-хендлер резолвит future по `correlation_id`.
4. Таймаут → авто-отказ (безопасный дефолт), пользователю уходит уведомление, что действие отменено по таймауту.

**Классификация риска** — статический список в конфиге:
- Bash: `git push`, `git commit --amend`, `rm -rf`, deploy-скрипты, `sudo`, `docker`, `systemctl restart|stop`
- Write/Edit по путям, содержащим `.env`, `credentials`, `secrets`, `*.pem`
- Всё остальное (чтение файлов, `grep`/`glob`, локальный `git commit`/`diff`, `ls`) — авторазрешено без подтверждения

### State/Persistence
SQLite (`aiosqlite`, как в остальных ботах пользователя): `active_project` на пользователя, `session_id` на проект (для `resume` в Agent SDK между сообщениями).

### Config
`pydantic-settings`: `TELEGRAM_BOT_TOKEN`, `ALLOWED_USER_ID`, `ANTHROPIC_API_KEY`, `PROJECTS` (маппинг имя → путь), `CONFIRMATION_TIMEOUT_SECONDS` (по умолчанию 600), список risky-паттернов.

## Поток данных

**Обычное сообщение:**
текст в Telegram → хендлер проверяет `ALLOWED_USER_ID` → определяет активный проект пользователя → `AgentManager` берёт/создаёт сессию (cwd проекта + `resume session_id`, если есть) → запрос в SDK, стрим ответа обратно в Telegram (редактирование сообщения по мере генерации; вывод длиннее лимита Telegram — чанками или файлом) → по завершении `session_id` сохраняется в SQLite.

**Рискованное действие:**
агент вызывает инструмент (например Bash `git push`) → `canUseTool` перехватывает до выполнения → классифицирует как risky → отправляет кнопки в чат → ждёт → ✅ разрешает выполнение, агент продолжает → ❌ или таймаут — агент получает отказ и сообщает пользователю, почему не может продолжить.

**Занятость по проекту:**
если для проекта уже выполняется запрос (agent loop не отработал), а пользователь пишет новое сообщение — `asyncio.Lock` на проект; бот сразу отвечает "ещё работаю над предыдущим запросом для `<project>`, подожди" вместо тихой очереди или потери сообщения.

## Обработка ошибок

| Сценарий | Поведение |
|---|---|
| Занятость по проекту | Lock на проект, немедленный ответ "ещё работаю, подожди" |
| Рестарт/краш процесса (systemd `Restart=always`) | In-memory стейт (futures, локи) теряется вместе с процессом — это ок; `session_id` на диске остаётся валидным, следующее сообщение продолжает через `resume` |
| Ошибки Anthropic API (rate limit, сеть) | Retry с backoff (`tenacity`); после исчерпания попыток — сообщение в чат + запись в лог |
| Лимит длины сообщения Telegram (4096 симв.) | Стриминг режется на чанки/редактируется по частям; длинный вывод (диффы) — отдельным файлом |
| Неверное имя проекта (`/project xyz`) | Бот отвечает списком доступных проектов из конфига |
| Сообщение не от `ALLOWED_USER_ID` | Тихо игнорируется, факт обращения логируется |
| Ошибка инструмента агента (упавшая bash-команда и т.п.) | Обрабатывается штатно самим Agent SDK (результат с ошибкой уходит в модель) — без special-case на нашей стороне |
| Логирование | Ротируемый файл-лог на VPS (`logging` + `RotatingFileHandler`), без отдельного дашборда |

## Тестирование

**Юнит-тесты** (`pytest` + `pytest-asyncio` + `pytest-mock`, как в `content-agent-bot`):
- Классификатор риска — таблица кейсов (`git push` → risky, `ls`/`git diff`/`git commit` → safe, запись в `.env` → risky, запись в обычный `.py` → safe).
- Confirmation Bridge — создание future, резолв по callback, срабатывание таймаута → auto-deny (Telegram и Agent SDK замоканы).
- State/persistence — сохранение/загрузка `active_project` и `session_id` через `aiosqlite` на tmp-файле.
- Хендлеры бота — мок `Update`/`Context`: сообщение от чужого `user_id` игнорируется; `/project unknown` → список проектов; `/project <valid>` → меняет активный проект.

**Ручной smoke-test на VPS после деплоя** (не автоматизируется — реальные Telegram/Claude API):
- Обычное сообщение → агент отвечает, читает `CLAUDE.md` проекта.
- Рискованная команда → приходят кнопки, ✅ выполняет, ❌ отменяет.
- Таймаут подтверждения → авто-отказ и уведомление в чате.
- `kill` процесса во время сессии → рестарт systemd → `resume` подхватывает контекст проекта.
- Переключение `/project` между двумя проектами → каждый помнит свой контекст отдельно.

## Открытые вопросы для реализации

Ни одного блокирующего — все ключевые решения по архитектуре зафиксированы выше. При реализации потребуется свериться с документацией Claude Agent SDK (`code.claude.com/docs/en/agent-sdk`) для точных сигнатур `query()`, `resume`, и формата `canUseTool` hook — это не покрывается общим skill'ом `claude-api` (он про Messages API/Tool Runner/Managed Agents, а не про Agent SDK).
