# Динамическое создание проектов из Telegram

**Дата:** 2026-07-26
**Статус:** черновик, ожидает review

## Цель

Сейчас у бота один жёстко прописанный в `.env` (`PROJECTS`) проект — `aleks`, каталог самого агента. Любая задача не по этому проекту (например, лендинг для стороннего бизнеса) заставляет бота работать внутри чужого кода и путаться, куда класть файлы. Нужна возможность создать новый проект прямо из чата, без ручного редактирования `.env` и рестарта сервиса.

## Контекст инцидента

Попытка попросить бота сделать лендинг привела к тому, что он застрял в каталоге `Aleks` и несколько раз подряд получил `Exception: Stream closed` на `mkdir`/`Write` — известная гонка control-канала в `claude_agent_sdk` (issue #1088), когда несколько tool-вызовов идут подряд в одном turn. Подробности и включённое DEBUG-логирование SDK — см. изменения в `app/main.py` от того же дня. Эта спека устраняет причину, по которой бот вообще оказывается в такой ситуации: создание файловой структуры нового проекта переносится из agent loop в детерминированный код бота, где эта гонка физически не воспроизводима.

## Область действия

- Триггер: сообщение пользователя начинается с одной из фиксированных фраз ("новый проект", "делаем новый проект", "создай/создать новый проект", "начнём/начнем новый проект"), дальше по тексту — название.
- Обработка триггера **не проходит через Claude** — папка создаётся, проект регистрируется и активируется чистым Python-кодом бота, до вызова `run_turn`.
- Список проектов после фичи = статический `settings.projects` (из `.env`) ∪ динамический список в `state.db`.
- Динамические проекты создаются в отдельном корне `PROJECTS_ROOT` (не внутри `/root/projects/Aleks`).

Вне области: удаление/переименование проектов из чата, редактирование `PROJECTS_ROOT` из чата, семантическое (LLM-based) распознавание триггера — только фиксированный список фраз.

## Архитектура

```
Telegram-сообщение
   │
   ▼
on_text_message (chat.py)
   │
   ├─ matches new-project trigger? ──yes──▶ handle_new_project()
   │                                          │  (Python, без Claude)
   │                                          ├─ slugify(name)
   │                                          ├─ resolve conflicts
   │                                          │    (статика/динамика/сам slug)
   │                                          ├─ os.makedirs(PROJECTS_ROOT/slug)
   │                                          ├─ state.add_dynamic_project(...)
   │                                          ├─ state.set_active_project(...)
   │                                          └─ ответ пользователю
   │
   └─ no ──▶ существующий флоу (get_active_project → run_turn → Claude)
```

### Триггер и slug

Regex (case-insensitive) вида:
```
^(?:давай\s+)?(?:делаем|создай|создать|начнём|начнем)?\s*новый проект[:\s]+(.+)
```
Захваченная группа — сырое название. `slugify()`:
1. Транслитерация кириллицы → латиница (стандартная таблица).
2. `lower()`, всё вне `[a-z0-9-]` → `-`, схлопнуть повторы дефисов, обрезать по краям.
3. Обрезка до 40 символов.

Так как slug строится только из белого списка символов, а не берётся из пути напрямую, path traversal (`..`, `/`) исключён по построению.

### Хранение и разрешение конфликтов

Новая таблица `state.db`:
```sql
CREATE TABLE dynamic_projects (
    name TEXT PRIMARY KEY,
    path TEXT NOT NULL,
    created_at TEXT NOT NULL
);
```

`StateStore` получает:
- `add_dynamic_project(name, path) -> None`
- `list_all_projects(static_projects: dict) -> dict[str, str]` — мердж статики и динамики (статика не переопределяется)
- `resolve_project_path(name, static_projects) -> str | None`

Правила при создании:
- Если `slug` совпадает с именем из `settings.projects` (сейчас — `aleks`) → не создаём, отвечаем "это имя занято системным проектом, выбери другое".
- Если `slug` уже есть в `dynamic_projects` → не создаём папку повторно, просто переключаем активный проект на существующий и говорим об этом явно ("проект уже существует, переключился на него").
- Иначе → создаём.

`/projects` и `/project <name>` (project.py) переключаются на `state.list_all_projects(settings.projects)` вместо голого `settings.projects`.

### PROJECTS_ROOT

Новая настройка в `config.py`:
```python
projects_root: str = Field(default="/root/user-projects")
```
При первом использовании создаётся (`os.makedirs(projects_root, exist_ok=True)`), если ещё не существует. Ошибка создания (нет прав, диск полон) → сообщение в чат, ничего не регистрируется в БД (создание папки — первый шаг, регистрация — только после успеха).

## Обработка ошибок

| Ситуация | Реакция |
|---|---|
| Триггер без названия после фразы | "Укажи название проекта в этом же сообщении: «новый проект <название>»" |
| Slug пустой после транслитерации (например, только эмодзи) | Та же реакция, что и "без названия" |
| Совпадение со статическим именем проекта | "Имя «aleks» занято системным проектом, выбери другое" |
| Проект с таким slug уже существует | Переключение на существующий + уведомление, без ошибки |
| `os.makedirs` упал (права/диск) | "Не получилось создать проект: <причина>", ничего не регистрируется |

## Тестирование

- Юнит-тесты `slugify()`: транслитерация, коллизии символов, пустой ввод, обрезка длины.
- Юнит-тесты `StateStore`: `add_dynamic_project`, `list_all_projects` (мердж + приоритет статики), повторное имя.
- Тесты хендлера (`tmp_path` как `PROJECTS_ROOT`): триггер создаёт папку и переключает активный проект без обращения к `run_turn`/`query`; конфликт с системным именем; конфликт с существующим динамическим проектом; сообщение без названия.
- Regex-тесты на все варианты триггерных фраз + on негативные случаи (обычное сообщение "новый проект" не должно ложно матчить фразы, которые лишь ссылаются на слово "проект").
