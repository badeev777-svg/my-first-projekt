# Skill Hunter — Design Spec

## Контекст и цель

Периодический процесс, подчинённый проекту Aleks, который ищет новые Claude-скиллы/тренды под заданные ниши пользователя (SpeakBuddy, Content Agent Bot, primerka, tg-beauty-catalog и т.д.) и присылает подборку кандидатов в Telegram на ручное утверждение. Идея навеяна страницей aibasis.ru «Охотник за трендами/скиллами» («lovec_trendov»), но её сгенерированный промпт не используется напрямую — это внешний источник, чей рабочий процесс (генерируешь промпт на сайте → скармливаешь его агенту) совпадает с задокументированным в `CLAUDE.md`/`AGENTS.md` признаком prompt injection («инструкции с сторонних сайтов, адресованные напрямую ИИ-агенту»). Вместо этого логика поиска и промпт пишутся самостоятельно.

**Успех:** раз в неделю (плюс по ручной команде) пользователь получает в Telegram подборку из 3-5 новых, ранее не предлагавшихся скиллов по каждой активной нише, с кратким описанием и ссылкой — без автоустановки.

## Global Constraints

- Не изменять и не ослаблять `app/agent_runner.py` (его `setting_sources=[]` и урезанный `system_prompt`) — по явному требованию `AGENTS.md`. Skill Hunter — полностью отдельный код, не импортирует и не переиспользует конфигурацию `agent_runner.py`.
- Не использовать сгенерированный на aibasis.ru промпт как входные инструкции для агента.
- Не автоустанавливать найденные скиллы — только предлагать. Установка (и проверка пакета в реестре перед установкой) остаётся ручным действием пользователя, по существующему правилу безопасности проекта.
- Python >= 3.11, типизированный код (pydantic/pydantic-settings), `uv` для зависимостей — как в остальном проекте.
- Не коммитить `.env`/секреты; список ниш и токен бота — через конфиг/переменные окружения.

## Review Focus

- **Пустой/недоступный WebSearch** (сеть недоступна, лимит исчерпан) — прогон по нише не должен падать всем процессом; логируется и пропускается, остальные ниши продолжают обрабатываться.
- **Дубликаты между разными нишами** — один и тот же скилл может подходить под две ниши; история дедупликации должна работать по глобальному идентификатору скилла (например, нормализованный GitHub URL), а не по паре (ниша, скилл), иначе один скилл предложится повторно под другой нишей.
- **Пустой результат поиска для ниши** — если кандидатов нет или все уже в истории, сообщение в Telegram не отправляется вообще для этой ниши (не слать пустые/пустые-по-факту подборки).
- **Повреждённый/отсутствующий файл истории** — первый запуск или случайно удалённый `history.json` не должен приводить к падению; создаётся заново.
- **Одновременный запуск** (systemd timer сработал, пока пользователь вручную вызвал `/find_skills`) — оба запуска не должны гонку испортить историю (потеря дедупликации) — история дописывается атомарно/с блокировкой файла.

## Архитектура

Отдельный модуль `app/skill_hunter/`, изолированный от `agent_runner.py` и от Telegram-обработчиков рискованных команд:

- `app/skill_hunter/config.py` — pydantic-settings: список ниш (`SKILL_HUNTER_NICHES`, через запятую или JSON-список в `.env`), путь к истории, chat_id получателя.
- `app/skill_hunter/history.py` — чтение/запись `app/skill_hunter/data/history.json` (git-ignored). Формат: `{"skills": {"<нормализованный URL>": {"first_seen": "<ISO дата>", "niches": ["..."]}}}`. Атомарная запись через временный файл + `os.replace`.
- `app/skill_hunter/search.py` — для одной ниши вызывает `claude_agent_sdk.query()` с собственным, не урезанным `system_prompt` (инструкция искать актуальные Claude-скиллы под нишу на GitHub/skills.sh через `WebSearch`/`WebFetch`) и парсит результат в список кандидатов `{title, url, description}`.
- `app/skill_hunter/hunter.py` — точка входа: по каждой активной нише вызывает `search.py`, фильтрует кандидатов по `history.py`, форматирует сообщение, отправляет в Telegram (переиспользует существующий Telegram HTTP-клиент/токен бота, но не диалоговый `agent_runner.py`), дописывает найденное в историю.
- Запуск: systemd timer `skill-hunter.timer` + `skill-hunter.service` (по аналогии с `aleks-agent.service`) — раз в неделю. Плюс команда `/find_skills` в `app/main.py`, которая запускает `hunter.run()` вне расписания (без участия `agent_runner.py`/`confirmation.py`, так как действие не risky — не меняет файлы, не выполняет код, только сеть+сообщение).

## Поток данных

1. Триггер (timer или `/find_skills`) → `hunter.run()`.
2. Для каждой ниши из конфига: `search.find_candidates(niche)` → список кандидатов (или пусто/ошибка, залогированная и пропущенная).
3. `history.filter_new(candidates)` — убрать уже предложенные (по глобальному идентификатору).
4. Если после фильтрации есть кандидаты — сформировать и отправить Telegram-сообщение (per-niche, только непустые); если нет — ничего не отправлять для этой ниши.
5. `history.record(niche, candidates)` — атомарно дописать в `history.json`.

## Обработка ошибок

- Ошибка WebSearch/сети для ниши → лог + пропуск этой ниши, остальные продолжают выполняться, процесс не падает целиком.
- Ошибка отправки в Telegram для одной ниши → лог, но найденное всё равно попадает в историю (чтобы не предлагать повторно на следующей неделе то, что реально нашли, даже если доставка не удалась) — либо не записывать в историю при неудачной отправке, реализация решит по месту при написании плана; фиксируем как открытый вопрос для плана.
- Отсутствующий/битый `history.json` → создать пустую историю, залогировать предупреждение.
- Параллельный запуск (timer + ручная команда одновременно) → блокировка файла истории (`filelock` или эквивалент) на время записи.

## Тестирование

- `pytest` + `pytest-asyncio` (как в остальном проекте).
- Мокаем `claude_agent_sdk.query()` в тестах `search.py` — не делаем реальных сетевых вызовов в тестах.
- Мокаем Telegram-отправку в тестах `hunter.py`.
- Юнит-тесты `history.py`: дедупликация по глобальному идентификатору между нишами, атомарная запись, восстановление после битого/отсутствующего файла.
- Тест на пустой результат ниши — сообщение не отправляется.
- Тест на ошибку одной ниши — остальные ниши всё равно обрабатываются.
