# sales-agent — дизайн первой версии

**Дата:** 2026-10-13
**Исходное ТЗ:** [ai-sales-build-brief.md](../../../ai-sales-build-brief.md) (материал Никиты Бархатова, Noya AI)
**Статус:** спецификация на ревью у владельца

## 1. Цель и решения владельца

ИИ-продажник: честно выясняет задачу клиента, подбирает вариант из утверждённого каталога, при согласии оформляет заявку и передаёт её человеку.

| Вопрос | Решение (2026-10-13) |
|---|---|
| Что продаёт | Движок + сменный каталог (`content/`). Первым наполняем услугами Александра (Badeev Agency) |
| Каталог | Черновик готовит Claude; все цены `approved: false` до подтверждения владельцем |
| Модель | GigaChat3.5 через cloud.ru Foundation Models (OpenAI-совместимый API, как в `../rag-demo/app/cloudru.py`); тонкий адаптер `llm_client`, второй провайдер не реализуется |
| Граница v1 | Локальный прототип + 14 сценариев приёмки. Docker-упаковка есть, деплой — отдельное решение |
| Проекты | В каталог входят все проекты, включая в разработке, со статусом |
| Aleks | Упоминается и описываются возможности; без ссылок, доступа и деталей инфраструктуры (`public: description_only`) |
| Маршрутизатор | Гибридный: приоритетные правила в коде → классификатор намерения (модель) → таблица допуска (код) |

Вне v1: оплата, CRM, мессенджеры, рассылки, холодные/повторные касания, публикация в интернет. `Manager-saler/` — предыдущая попытка, будет удалена владельцем позже; используется только как источник вилок цен.

## 3. Данные каталога

### services.yaml
Поля: `id, title, description, includes[], price_from, price_to, currency, period (one_time|monthly), duration_note, approved (bool), source`.
- Цена попадает в ответ клиенту только при `approved: true`. Иначе бот говорит, что цену уточнит менеджер.
- Если у одного `id` в источниках две разные цены → `catalog.py` помечает конфликт, цена не выдаётся, вопрос уходит человеку.

Черновик (все `approved: false`):

| id | Услуга | Вилка | Источник |
|---|---|---|---|
| ai-consultant-gigachat | ИИ-консультант на GigaChat (152-ФЗ) | 150–300 тыс. ₽ + сопровождение | стратегия 2026-09-26 |
| ai-agent | AI-агент под заказ | 50–200 тыс. ₽ | Manager-saler |
| tg-bot | Telegram/MAX-бот под заказ | 20–150 тыс. ₽ | Manager-saler |
| rag-docs | Ответы по документам компании (RAG) | нет цены | — |
| automation | Автоматизация бизнес-процессов | 30–120 тыс. ₽ | Manager-saler |
| landing | Лендинг / продающий сайт | 15–50 тыс. ₽ | Manager-saler |
| e-shop | Интернет-магазин | 50–150 тыс. ₽ | Manager-saler |
| lead-parser | Lead Parser | 30–80 тыс. ₽ | Manager-saler |
| content-agent | Content Agent Bot | 2 499 ₽/мес или от 80 тыс. ₽ | Manager-saler |

Не переносятся из Manager-saler неподтверждённые обещания результата («−60–80% нагрузки», «заменяет SMM-специалиста», «напишет в течение часа»).

### projects.yaml
Поля: `id, title, description, status (live|in_dev|paused), url (optional), public (yes|no|description_only), verified (bool)`.
- `in_dev`: бот говорит «в разработке», не называет сроков, не продаёт как готовый продукт; может предложить похожее решение под заказ или передать человеку.
- `description_only`: только описание возможностей, без URL и деталей.
- `public: no` в промпт не попадает.
- В каталог входят все папки-проекты, кроме личных/служебных (claude-memory, thoughts, Manager-saler, docs, knowledge, memory). Описания проектов с неизвестным назначением составляются по коду и помечаются `verified: false`.

### faq.yaml, policy.yaml
FAQ: `q, a, approved`. Неутверждённые ответы не используются как факт. Policy: тон («вы», коротко), получатель заявок («Александр»), текст согласия на передачу контакта, правила данных. Без согласованного текста согласия сбор реальных контактов выключен (в демо — только синтетика).

## 4. Поток одной реплики

1. **Вход (код).** Длина ≤ 2000 символов, rate limit, `conversation_id` принадлежит сессии (cookie) — иначе 403, модель не вызывается.
2. **Приоритетные правила (код).** `stopped` → без ответа; `human_pending`/`closed` → без продающих ответов; явная просьба о человеке / отказ / попытка взлома → соответствующая ветка.
3. **Классификатор (модель).** Выход: `intent ∈ {question, need, price, objection, agree, refuse, human, other}`. Невалидный выход → `other`.
4. **Допуск (код).** Таблица `(state, intent) → skill`. Недопустимое сочетание → безопасный навык (discovery или handoff).
5. **Навык (модель).** Промпт = `role.md` + `SKILL.md` + факты каталога, отобранные кодом (только `approved` и `public`). Ответ — JSON-контракт: `reply, facts_used, missing_fields, next_state, proposed_action, review_status`.
6. **Проверка (код + модель).** Схема; каждая цифра/цена в `reply` есть среди отобранных фактов; `next_state` допустим; нет секретов/чужих данных. При сомнении — sales-quality-check (`pass | revise | human_review`); не более одного `revise`.
7. **Действие (код).** `proposed_action` — предложение, не команда. Заявка и передача создаются только кодом с ключом уникальности; «отправлено» — только после успешного ответа операции.

### Состояния
`new, discovery, offer, consent_pending, lead_draft, human_pending, closed`.

```
new → discovery ⇄ offer → consent_pending → lead_draft → human_pending → closed
любое → human_pending   (просьба о человеке, жалоба, конфликт данных, вне полномочий)
любое → closed          (отказ) — повторных продаж нет
```
Выход из `human_pending` — только явное действие ответственного в `/admin`.

### Ошибки
- Таймаут модели 20 с, 1 повтор; затем понятное сообщение, состояние не меняется.
- Повтор той же реплики (`client_message_id`) возвращает сохранённый ответ.
- Сбой передачи → статус «передача не подтверждена», без ложного успеха.

## 5. Хранилище (SQLite)
Таблицы: `conversations(id, session_id, state, stopped, created_at)`, `messages(id, conversation_id, client_message_id UNIQUE, role, text, skill, created_at)`, `leads(id, conversation_id, idempotency_key UNIQUE, contact_masked, contact, consent_status, consent_time, need, product_id, next_step, delivery_status)`, `handoffs(id, conversation_id, idempotency_key UNIQUE, reason, summary, question, delivery_status)`.

## 6. Интерфейс
- `index.html`: сообщения, индикатор ожидания, понятные ошибки, повтор без дублей, «Сбросить диалог», «Остановить автоответы». Плашка «Демо — модель не подключена» в режиме DEMO.
- `admin.html` (только localhost): список заявок и передач, возврат управления из `human_pending`.
- Адаптивность: телефон и компьютер.

## 7. Безопасность
Ключ только в `.env` на сервере; секреты не попадают в ответы, URL, фронтенд, логи. Контакты в логах маскируются. Текст клиента — недоверенные данные, вывод экранируется. Диалоги изолированы по сессии. `/admin` — только `127.0.0.1`. Режим DEMO без ключа: шаблонные ответы, `delivery_status: demo`.

## 8. Тестирование и приёмка
- **Юнит-тесты** (фейковая модель): state, catalog, validators, leads, router.
- **14 сценариев ТЗ** через HTTP с фейковой моделью, включая «плохие» ответы модели (выдуманная цена, утечка секрета, таймаут) — доказывают, что защиту держит код.
- **Живая приёмка:** `scripts/live_acceptance.py` на GigaChat → `docs/acceptance-report.md` (вход / ожидаемо / фактически / статус: авто / вручную / не проверено).
- Вёрстка: Playwright-скриншоты телефон + десктоп.

## 9. Результат для владельца
Локальная демонстрация (`start.bat` и Docker), список файлов, README без предположения о навыках терминала (где менять прайс, роль, проекты), отчёт по 14 сценариям, ограничения, требования для одного реального канала.

## 10. Не проверено
- Тарифы cloud.ru на GigaChat3.5 (в agent-hub тоже не проверены).
- Строгость следования GigaChat3.5 JSON-контракту — выяснится в живой приёмке; защита на стороне кода не зависит от этого.
